# MacTouch protocol v1

Status: implemented by `desktop/` (Swift), `mobile/` (Dart) and `protocol/tools/reference.mjs` (Node).
Shared test vectors: `protocol/test-vectors.json` (generated by `tools/gen_vectors.py`; all three implementations assert against it).

## Transport

- WebSocket (RFC 6455), plain `ws://`, on the local network. Default port **48500**.
- Text frames only. Each frame is one UTF-8 JSON object, max **16 KiB**; larger or non-text frames are ignored/refused.
- Every message has `"type"` (string) and `"v"` (integer protocol version, currently `1`).
- The Mac is the server. The phone is the client. One authenticated phone at a time.

Because the transport is not encrypted, **no secret is ever sent**. Authentication uses HMAC-SHA256 proofs over fresh nonces (below).

## Encodings

- `base64url` = RFC 4648 URL-safe alphabet, **no padding**.
- `token`: 32 random bytes. `nonce`: 16 random bytes. `secret`: 32 bytes (HMAC output).
- IDs (`deviceId`, `serverId`) and nonces match `[A-Za-z0-9_-]{8,64}`.
- HMAC key = the raw bytes (decoded), message = UTF-8 string.

## QR payload

The Mac renders this JSON (compact, UTF-8) as a QR code:

```json
{"app":"mactouch","v":1,"host":"192.168.1.20","port":48500,
 "token":"<base64url 32 bytes>","exp":1790000000,"name":"Mac mini","id":"<serverId>"}
```

| Field | Rule |
|---|---|
| `app` | must equal `"mactouch"` |
| `v` | integer; phone refuses anything other than the version it speaks (with a specific "update the app" message) |
| `host` | IPv4 literal in 10/8, 172.16/12, 192.168/16 or 169.254/16 (public addresses and hostnames are refused) |
| `port` | integer 1024–65535 |
| `token` | base64url, decodes to exactly 32 bytes |
| `exp` | unix seconds. The Mac enforces expiry; the phone only skips obviously stale codes (30 s skew allowed) |
| `name` | 1–64 chars, shown to the user |
| `id` | stable Mac identity; the phone pins it and refuses a different Mac on reconnect |

Token lifetime is **120 s**, **single use**, and rotates after every pairing attempt that consumed it, after expiry, and after 5 bad proofs.

## Messages

| Direction | `type` | Fields |
|---|---|---|
| Mac → phone | `challenge` | `serverNonce`, `serverId`, `serverName` (sent immediately on connect) |
| phone → Mac | `pair_request` | `deviceId`, `deviceName`, `clientNonce`, `proof` |
| Mac → phone | `pair_pending` | – (token accepted; waiting for the user to approve on the Mac) |
| Mac → phone | `pair_accepted` | `serverProof` |
| Mac → phone | `pair_rejected` | `reason` |
| phone → Mac | `auth` | `deviceId`, `clientNonce`, `proof` |
| Mac → phone | `auth_ok` | `serverProof` |
| Mac → phone | `auth_failed` | `reason` |
| either | `ping` / `pong` | – (phone pings every 10 s; Mac drops a silent session after 30 s) |
| either | `disconnect` | – |
| Mac → phone | `error` | `reason` or `code` |

`reason` values: `token_expired`, `invalid_proof`, `declined`, `busy`, `timeout`, `unknown_device`, `bad_message`, `unauthenticated`, `internal_error`. Unknown values are treated as a generic rejection.

## Handshake math

```
pairProof   = HMAC(token,  "pair|"   + deviceId + "|" + clientNonce + "|" + serverNonce)
secret      = HMAC(token,  "secret|" + deviceId + "|" + clientNonce + "|" + serverNonce)   // derived locally, never sent
authProof   = HMAC(secret, "auth|"   + deviceId + "|" + clientNonce + "|" + serverNonce)
serverProof = HMAC(secret, "server|" + serverNonce + "|" + clientNonce)
```

All comparisons are constant-time.

### Pairing (first connection)

```
phone                                    Mac
  | -- WebSocket connect -------------->  |
  | <-- challenge(serverNonce, serverId)  |  phone checks serverId == QR id
  | -- pair_request(deviceId, name,       |
  |       clientNonce, pairProof) ------> |  Mac verifies proof with the QR token, consumes it,
  | <-- pair_pending -------------------  |  shows the confirmation dialog (60 s)
  |                                       |  user approves: Mac derives + stores secret (Keychain)
  | <-- pair_accepted(serverProof) -----  |  phone derives the same secret, checks serverProof
```

`serverProof` proves the Mac knew the token, so a rogue device on the LAN cannot impersonate the Mac to a freshly-scanned phone.
The phone stores the secret only after `serverProof` verifies (Android Keystore via `flutter_secure_storage`).

### Reconnect

```
phone                                    Mac
  | <-- challenge(serverNonce, serverId)  |  phone checks serverId == pinned id
  | -- auth(deviceId, clientNonce,        |
  |       authProof) -------------------> |  Mac loads secret by deviceId, verifies
  | <-- auth_ok(serverProof) -----------  |  phone verifies serverProof
```

If the same phone reconnects while its old session is still open (e.g. after a Wi-Fi change), the old session is replaced. A different phone gets `auth_failed: busy`.

## Authentication gate

Until a session is `authenticated`, the Mac accepts only `pair_request` and `auth`. Anything else gets `error: unauthenticated` and the socket is closed.
Unauthenticated sockets are closed after 15 s; at most 8 unauthenticated sockets are held at once.
After authentication, message types not implemented by the Mac get `error: unsupported` (input commands arrive in Part 2).

> **Part 2 update:** frames after the handshake are now signed and replay-protected; see [INPUT.md](INPUT.md).
> The "does not hold yet" list below is superseded, except that frames are still not encrypted.

## Security properties and known limits (v1)

Holds:
- A passive eavesdropper on the Wi-Fi learns no token, secret or reusable proof (proofs are bound to fresh nonces).
- A device that never saw the QR code cannot pair; a stolen `deviceId` is useless without the secret.
- The user must approve each new phone on the Mac.
- Tokens expire, are single-use, and are rate-limited (5 bad proofs).

Does **not** hold yet (planned before any input command ships in Part 2):
- Frames after the handshake are neither encrypted nor individually authenticated. An attacker who can hijack the TCP stream on the LAN could inject frames into an authenticated session. Part 2 will derive a session key (`HMAC(secret, "session|"+clientNonce+"|"+serverNonce)`) and add a per-frame sequence number + MAC before the first control message is accepted.
- Someone who photographs the QR code while it is valid can pair, but only if the Mac's owner then clicks "Pair".
